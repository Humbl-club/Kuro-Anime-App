# Kuro production workload — 100 active users

Target chosen by owner: **100 simultaneous active users**. Run from the local Mac against the existing Frankfurt project, without plan upgrades or paid AI/provider work. Postman CLI/MCP are unavailable; the repository's Node tooling supplies a repeatable fixed-arrival workload rather than the old unpaced Concierge loop.

Qualification model (set before the capacity run): 100 distinct disposable authenticated identities, each active roughly once every five seconds = **20 requests/second**. The peak profile offers **40 requests/second**, or one request per active user every 2.5 seconds. This is 100 active sessions with realistic think time, not a claim of 100 continuously busy database queries. The fixed-arrival scheduler records missed starts and client saturation instead of silently reducing traffic when responses slow.

Fixture: 20 empty libraries, 50 with 25 titles, 25 with 100 titles and 5 with 2,000 titles; 70% anime / 30% manga. Total 13,750 temporary list rows. Fifty users share five private clubs of ten. Catalogue data is the real production catalogue, sampled across popular titles. Administrative credentials are used only for fixture setup/cleanup; measured traffic uses ordinary user tokens. Account/club inventory and tokens stay in a mode0600 file outside the repo. No existing customer's private data or resources are mutated.

Request mix: Home20%, Browse20% (four sorts and some genre refinements), Search15% (varied queries), Detail20% (skewed popular/title variety), moods8%, clubs5%, Discover5%, progress writes5% (empty accounts revisit Home), Parse1%, deterministic Recommend1%. Both media are represented. Discover writes impressions and progress writes must return an applied mutation receipt. Requests are not allowed to succeed on status alone. No spoofed IPs, service-role workload calls, disabled guards, or automatic retries.

Initial profile: low-rate wiring, then 2/5/10/20rps short ramps after fixture setup. If safe, ten-minute20rps steady state, bounded40rps spike, and recovery. The runner refuses above50rps,100 VUs,600 seconds/run or20,000 starts/run. The low-rate empty-account wiring check is not capacity evidence. Setup/cleanup are capped at4 request starts/second and run separately from load.

Thresholds, measured end-to-end from this generator: zero unexpected errors/timeouts, zero dropped offered starts; p95 Browse/Search/Clubs/Progress ≤750ms, Home/Detail ≤1200ms, Discover/Moods ≤1500ms, Edge Parse/Recommend ≤2500ms. All completions, including errors and timeouts, enter the latency distribution. Report per-endpoint sample sizes; sparse Edge samples do not prove paid narration capacity. Near-minimum throughput is offered traffic minus bounded drain time, with achieved/successful rps reported independently.

Safety stop: stop new starts on ≥3 failures in the last50 completions (once20 exist), or ≥5 replies taking >5s; each request has an8s deadline. Database monitoring records active/total sessions, lock waits, oldest query, deadlock/temp-I/O deltas and normalized query-stat deltas. Stop and investigate sustained connection/lock pressure before increasing rate. Counters are not reset. Existing scheduled ingestion remains enabled so natural background work is included when it overlaps.

Keep every original failed run. A bottleneck fix needs source review, relevant regression/SQL-plan checks and exact live deployment evidence before the same workload is repeated. Applied migrations are immutable. A local large-data query plan is separate from hosted concurrent-user evidence. Full corpus replay, native/device, CDN/image bytes, Realtime delivery, authentication floods, external import-provider bursts and arbitrary larger user counts are outside this capacity claim and must remain identified as limits.
