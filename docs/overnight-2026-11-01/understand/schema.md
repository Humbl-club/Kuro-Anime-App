## 1. Executive summary (ranked)

1. **97.4% of all DB execution time is the 5-minute similar-titles driver.** That is 183 h over 88 days: 25,395 calls, about 26 s each (`live/outliers.txt`, row 1). Every fire rebuilds the global franchise graph before it checks whether any work is pending (`20260807010000_leftover_repairs_v1.sql:243` defines the function; the recursive graph is at :316; the empty-batch early return is at :418). A nightly job also marks all ~7.5k seeds stale (`20260804130000_media_similar_titles_precompute.sql:1416-1420`), which forces about 76 heavy fires a day. The fix is mechanical and the risk is low. **P0, needs live deploy.** (This agrees with Sep audit §1, which measured the same cost a month earlier. Nothing has changed since.)
2. **Several large tables are mostly unread weight.**
   - `catalog_safety_audit` is 131 MB, append-only, with no retention. It is never read (0 seq scans), and its 2×18 MB indexes have 0 scans.
   - `chapters` is 94 MB. Most rows are "Chapter N" placeholders created by bulk import (`bulk-import-manga/mapping.ts:113-126`, default 120 per manga at `bulk-import-manga/handler.ts:34`). It carries two **unique indexes on always-null columns** (`chapters_anilist_id_key`, `chapters_mal_id_key`, 6 MB each).
   - `volumes` (8.8 MB) is placeholder-only and never read: every index has 0 scans and there is no iOS or RPC reader.
3. **Write amplification on `anime`/`manga` (PLAUSIBLE, likely the main heap-bloat driver).** The causal chain:
   - Every "unchanged" hourly import still runs `update manga set last_synced_at=…` (`bulk-import-manga/mapping.ts:42`). Chapter enrichment does the same every 15 min (`manga-chapter-enrich/repository.ts:416-428`).
   - The BEFORE UPDATE trigger `update_updated_at_column` unconditionally sets `updated_at = now()` (`baseline_capture_v1.sql:1866-1874`, triggers at :1911 and :2021).
   - `updated_at` is a key column of the four synopsis queue indexes (`baseline_capture_v1.sql:1765-1766,1810-1811`).
   - So every touch is a **non-HOT update that writes into all ~25 indexes** on each table.
   - Two of the four "weekly" import crons actually run hourly (`kuro-import-anime-weekly 0 * * * *`, `kuro-import-manga-weekly 10 * * * *` in `research/.../live-cron.json`).
4. **Search and Browse cannot use any index.**
   - Every trigram and full-text title index was dropped at `20260216200227_drop_unused_indexes_merge_policies_health_check.sql:6-17`. This includes the manga genres GIN, which went in the same file. (Sep audit §3 cites these trgm indexes as existing. That was already wrong when it was written: the drop is from February, and that audit's own `research/.../live-indexes.json` lists no trigram or full-text index on `anime`/`manga`.)
   - Browse orders by a `CASE … coalesce(popularity,0)` expression (`20260326234000_exclude_ancillary_anime_from_default_surfaces.sql:505,628`). No btree can serve that ordering, so every page is a full table scan plus a sort.
5. **Releases and songs: the tables exist, the data does not.**
   - `release_events`, `theme_links` and `catalogue_units` each have an 8 kB heap. That is one allocated page, so a few probe or manual rows may exist, but they are not populated at scale (Q5).
   - The theme producer (`scripts/series_enrichment_worker.py`) has not run at scale; 3,678 jobs are queued in `series_enrichment_jobs`. HANDOFF.md:139 says "No backfill or worker scheduling occurred".
   - Manga next-chapter fields are **hard-coded to null on every import** (`bulk-import-manga/mapping.ts:66-67`). `idx_manga_next_chapter` therefore indexes an all-null column.
   - The schema can hold a basic OP/ED list. It cannot hold episode ranges, versions or music links, or estimated-vs-confirmed releases with confidence. Section 3 has the exact gaps and an additive migration.
6. **A latent correctness bug in the legacy-unit bridge (PLAUSIBLE).**
   - The bridge keys `catalogue_units` ownership on the surrogate `episodes.id` (`series_home_foundation_v1.sql:3467`).
   - The airing import deletes and re-inserts all episodes of a title (`bulk-import-anime/mapping.ts:123-147`).
   - After one such cycle, the delete trigger has marked each unit `available=false` and written a `withdrawn` release event. The re-inserted episode then has a new id, so its provenance no longer matches and it can never update its unit again (:3477 and :3483, `where catalogue_units.source_provenance=excluded.source_provenance`).
   - **This must be fixed before any backfill or episode re-import runs against the bridge.**
7. **Join-table re-imports fail silently (CONFIRMED in code; live rate UNVERIFIED).** `anime_tags`, `anime_studios`, `anime_characters`, `anime_staff` and `manga_tags` are upserted **without `onConflict`** (`bulk-import-anime/mapping.ts:156,170,186,202`; `bulk-import-manga/mapping.ts:172`). PostgREST then arbitrates on the surrogate PK `id`. A re-import collides with the `(x_id, y_id)` unique key (23505). `noteOptionalFailure` only increments `results.errors` and calls `console.error` (`bulk-import-anime/mapping.ts:9-14`), so tag ranks and staff/character roles never update after first import. Live rate: check edge logs for `anime_tags upsert error:` / `anime_studios upsert error:` and the `errors` counter in `import_runs.results` (Q11).
8. **Duplicate indexes:** about 20 exact duplicates of a PK or unique key (section 5.1), roughly 30 MB. The drop is safe and carries no behaviour change.
9. **RLS is sound on all 132 tables**: RLS is enabled everywhere, and service-only tables have no policies. The findings are low priority: bare `auth.uid()` initplan policies on 5 tables, duplicate ALL policies on the dead `anime_comments`, and internal moderation columns readable by anon (section 7).
10. **Planner statistics may be missing (UNVERIFIED).** `table-stats.txt` shows "Estimated row count 0" for clearly populated tables (`manga`, `external_links`, `episodes`, all join tables, `catalog_safety_audit`). If that column is `pg_class.reltuples`, these tables have never been ANALYZEd and every RPC join is planned on default estimates. If it is `n_live_tup` since the stats reset, it means only "no vacuum/analyze since reset". Either way, run Q1 and then `ANALYZE`.

### 3.3 Can it hold confirmed vs estimated next release (episode/chapter/volume) with source and confidence?

**Not cleanly.** `release_events` has `status` and `precision` (good). It lacks:
- a **unit kind and number** (`kind` is free text such as `'Episode 5'`, built at :3489);
- a **basis**: confirmed by the provider schedule, announced by the publisher, or projected from cadence;
- a numeric **confidence**;
- a structured **source / provider / source_url / observed_at** (`evidence` is a string; `source_identity` is a dedupe key);
- a **unit range** (for example, chapters 120–122 releasing the same day, or volume N containing chapters a–b).

Two read-path problems will appear as soon as the table is populated:
- **Estimated events are invisible.** `home_events_page_v1` surfaces only `status in ('scheduled','announced')` (:3383).
- **Neither partial index can serve the Home RPCs.** Both RPCs join `tracked t on t.id = coalesce(r.anime_id, r.manga_id)` (:3382, :3437). The `coalesce` prevents use of `idx_release_events_anime_time` (anime_id, utc_instant) and `idx_release_events_manga` (manga_id, status). Today that is harmless because the table is empty.

`volumes.release_date/release_at/isbn` could hold real next-volume dates, but there is no producer and no reader.

### 3.4 Proposed additive migration (P1; needs live deploy; no destructive change)

```sql
-- 1) release_events: machine-readable unit + basis + confidence + source
alter table public.release_events
  add column if not exists unit_kind text
    check (unit_kind in ('episode','chapter','volume','season','film','special','other')),
  add column if not exists unit_number numeric,          -- 10.5 chapters, episode 0
  add column if not exists unit_number_end numeric,      -- multi-unit drops / volume ranges
  add column if not exists basis text not null default 'source_schedule'
    check (basis in ('source_schedule','publisher_announcement','projected_cadence','user_reported','legacy_bridge')),
  add column if not exists confidence numeric(4,3) check (confidence between 0 and 1),
  add column if not exists source text,                   -- 'anilist_airing','mangaplus','openbd','animethemes',...
  add column if not exists source_url text,
  add column if not exists observed_at timestamptz;
-- keep 'status' semantics; estimated = basis='projected_cadence' (+ confidence), never a new status value

-- serve per-medium tracked joins (replace coalesce(anime_id,manga_id) with two UNION ALL branches)
create index if not exists idx_release_events_manga_time
  on public.release_events (manga_id, utc_instant)
  where manga_id is not null and utc_instant is not null;
create index if not exists idx_release_events_upcoming
  on public.release_events (medium, utc_instant)
  where status in ('scheduled','announced') and utc_instant is not null;   -- global calendar / "airing today"

-- 2) theme_links: entry-level coverage + flags; links as child rows
alter table public.theme_links
  add column if not exists version integer,
  add column if not exists episodes_raw text,            -- keep source text verbatim
  add column if not exists episode_start integer,
  add column if not exists episode_end integer,
```

## 8. `user_id` TEXT vs UUID

TEXT `user_id`, with no FK to `auth.users`:
- `anime_user_lists`, `manga_user_lists`, `anime_comments`, `manga_comments` (baseline);
- `concierge_events` (`20260211100000_rag_tables.sql:248`);
- `rag_retrieval_feedback` (:213);
- `discover_rail_impressions` (`20260326234000…:692`);
- and **four new foundation tables that chose TEXT to match the lists:** `home_publications`, `list_entry_tombstones`, `mutation_receipts`, `user_series_intent` (`series_home_foundation_v1.sql:47,150,258,393`).

Everything else is UUID, mostly with `references auth.users`.

Consequences:
- No FK cascade on account delete; deletion relies on `delete_user_concierge_data` / `delete-account` sweeps.
- Case sensitivity. Swift `uuidString` is upper-case; this is handled by the canonical-case trigger (`20261005180000…`, likely live, Q9) and by the client lowercasing (`FeatureFlags.swift:128`).
- Casts in joins (`count_friends_tracking`).

**Recommendation:**
- Do not migrate the legacy list tables now; it is a high-risk table rewrite.
- **Add `check (user_id = lower(user_id) and user_id ~ '^[0-9a-f-]{36}$') not valid`** to the TEXT tables. Validate later, after the opt-in backfill (`prepared-migrations/opt-in/20261005180100_list_user_id_lowercase_backfill.sql`).
- New tables should use UUID with an FK. Bridging to TEXT list tables should use `auth.uid()::text` at the comparison site.
