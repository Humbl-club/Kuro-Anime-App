# Tracker gaps: design and success parameters (2026-11-09)

**Status:** spec for owner review. Nothing in this document is built, applied, deployed or flagged.
**Why:** the 2026-11-09 competitor research (app-store reviews, MAL/AniList/Simkl forums, Lemmy, Hacker News, archived manga Reddit) ranked what drives people away from list trackers, and compared each item with Kuro. This spec turns the five quick wins and five bigger items from that comparison into scoped, testable workstreams.
**Earlier research this builds on:** `docs/research/2026-09-25-anime-tracking/RESEARCH_AND_DECISIONS.md` (its decisions are binding where quoted below).
**Plans:** `docs/superpowers/plans/2026-11-09-tracker-gaps/` (`00-program.md` is the entry point).
**Acceptance specs:** `docs/superpowers/specs/2026-11-09-tracker-gaps/features/*.feature` (one per workstream; every scenario maps to exactly one test, see §4).

## 3. Binding constraints (copied from the repository; every task inherits them)

**Capacity and latency** (`docs/backend-load-2026-11-09/PLAN.md`, owner-selected target):
- Target: **100 simultaneous active users**; steady **20 requests/second**, peak **40 requests/second**.
- p95 end-to-end thresholds: **Browse/Search/Clubs/Progress ≤ 750 ms, Home/Detail ≤ 1200 ms, Discover/Moods ≤ 1500 ms, Edge Parse/Recommend ≤ 2500 ms**; zero unexpected errors/timeouts, zero dropped offered starts.
- Current status: **NOT QUALIFIED.** Latest run R13 (`capacity-verdict-r13.json`, 2026-11-09): 12,300 completions, 0 errors, 0 dropped in the ten-minute 20 rps soak, but the 2,000-title Recommend subgroup failed (p95 2,614 ms vs 2,500 ms, from 3 samples) and the sequence stopped before burst/recovery.
- Rule for this program: every new or changed backend read/write is assigned to one existing budget class, added as an F3 load profile, and covered by an SQL-plan check. Release follows D-H. Budgets are never relaxed for a retry.
- **Load model:** the predeclared qualification mix keeps its absolute arrival rate (20 rps) when profiles are enabled; profiles add their own absolute rates in a separate lane and are reported separately, so the base comparison is like-for-like. The combined workload `tracker-gaps-combined` states each profile's rate explicitly (guest traffic as an absolute rate, not a share).
- **Release evidence** comes only from qualification mode: populated fixtures (no empty-answer passes), semantic assertions, representative writes (organisation saves, list create/reorder/rebalance/seed, status with date fill), typical and supported-maximum payloads, cleanup verification, and minimum samples of **≥ 100 completions per endpoint and ≥ 30 per library-size subgroup** (fewer → `insufficient`, never `pass`). Wiring mode may accept empty answers and is never release evidence.
- Known limit of the model: it qualifies a declared request mix, not every way 100 people can use the app; measuring request fan-out per screen action belongs to the load-qualification track (September full review §client audit) and is not a precondition for each workstream.
- On-device budgets in this spec are **proposed, confirm after baseline** (the September full review forbids inventing budgets): measure first on the owned simulator `7FC4B58A-430C-457D-A017-6B0095723F3F`, record the baseline in the plan's evidence folder, then set the gate.

**Architecture** (CLAUDE.md Rule 4 + modular architecture): one `@MainActor @Observable final class` owner per capability in `Kuro/<Capability>/`, built once in `AppComposition`; views read owners with `@Environment(Type.self)` and import no Supabase SDK module; account-scoped owners conform to `AccountScopedState`, capture `AccountContext` at the start of every async operation and check `isCurrent` before every private write, and are registered in `makeAccountScopedStates`; every new private SDK request runs inside `accountSession.withCredentialLease(for:)` (`Packages/KuroModules/Sources/KuroCore/AccountSession.swift`), because an `isCurrent` check before publishing cannot stop an old payload being sent with newly installed credentials; Undo only undoes what its action created (receipt bound to the created entry's row id, lifecycle id and revision; refused after any intervening change); writes from a possibly stale client are deltas or carry an expected revision, never whole-set replacements; tracking reads/writes only through `LibraryStore` / `LibraryActions`; no second Supabase client; no Combine; `print` only inside `#if DEBUG`; no force unwraps.
**Navigation and Discover:** Rule 5 (navigation contract) and Rule 6 (Discover R1–R8) apply to every new screen, sheet and tap target. New sheets register `.kuroNavigationLayer`; tool sheets use `.kuroLeavesJourney()`; unsaved input uses `.kuroDiscardGuard`.
**Copy and design:** every user-facing string through `KuroLocale` (EN + DE); monochrome only, no coloured status; branded states only (`check_branded_states.sh`); light only until W8 ships.
**Database:** RLS on every new table; every function `SET search_path = public, extensions`; no raw `user_id` from clients; SECURITY DEFINER functions grant EXECUTE only to the roles that need it and revoke PUBLIC (see `20261108120159_review_security_v1.sql`); new SQL bodies in plpgsql (fixture rule); error codes in MESSAGE or HINT, never DETAIL alone. Migrations are written to `supabase/prepared-migrations/` and applied only after explicit owner approval; never `supabase db push --include-all` or history repair without a new approval. Account deletion (`delete-account`) must remove every new per-user table.
**Business rules** (RESEARCH_AND_DECISIONS, P0): "Kuro will not charge for tracking, ordinary discovery, search/filter/sort, history, import/export or useful reminders." "No upgrade modal, artificial daily tracking limit, reward-ad requirement, paid export or pay-to-sort mechanism."
**Data rules** (RESEARCH_AND_DECISIONS): "Group franchises without throwing away season-level detail that some users explicitly like." "Preserve imported IDs through grouping and export." "Optional automation needs an identity preview, queue visibility, conflict policy and undo." "Explain local-only guest saving." "Do not interpret missing source history as newly deleted data."
**Notifications:** D14 as written (`docs/superpowers/specs/2026-11-03-details-songs-platform-design.md` §D14) until the owner amends it via D-B: only exact confirmed/announced instants notify; only the Profile toggle and the detail bell may ask for permission; default off; cleared on sign-out.
**Continuity:** `SeriesGrouping.decide` — "A provider relation, a shared title or a calendar season is not membership." Only reviewed continuity joins a group.
**Process:** Rule 1 (three state docs) and Rule 2 (memory) after every workstream; quality gates `scripts/quality-gates/run_all.sh` green; build warning count does not rise above the 2026-10-31 baseline (60 unique Kuro-side warnings).

## 4. BDD + TDD method

**Outside-in.** Each workstream has a Gherkin `.feature` file (the behaviour the owner accepts). Each scenario carries exactly one tag naming the test that proves it. Implementation then proceeds test-first inside each task (red → green → commit).

**Workstream attribution.** A scenario belongs to the workstream named by the feature file's basename up to its first `-` (`W9-lists.feature` → `W9`, `W3-alerts.feature` → `W3`), unless the nearest `@workstream-<ID>` tag (Scenario, then Rule, then Feature) names another one (the F2 Rule of `W9-lists.feature` carries `@workstream-F2`). That id is the `<workstream>` of the execution record `docs/tracker-gaps-2026-11/acceptance/<workstream>.json` and of `check_bdd_traceability.py --accepted <workstream>` (F1.1/F1.3).

**One test per scenario, at the cheapest layer that proves it:**
1. `@pkg:<Suite>/<test>` pure rule or store test in `Packages/KuroModules/Tests` (`swift test`).
2. `@swift:<Suite>/<test>` app test in `KuroTests` (Swift Testing; owners with fake transports, render tests).
3. `@sql:<file>` local database test in `supabase/tests/` (`scripts/db/run_local_db_tests.sh --only <name>`).
4. `@deno:<path>::<test name>` Edge Function test.
5. `@ui:<Class>/<test>` offline UI test (`--kuro-nav-fixture` / `FixtureHost`), only for journey-level scenarios.
6. `@load:<profile>` a named profile `scripts/load/profiles/<profile>.js`, registered through `TRACKER_GAP_PROFILES` in `scripts/load/backend_workload.js` and listed with its rate in the `tracker-gaps-combined` workload (capacity scenarios; accepted only from a qualification-mode run).
7. `@manual:<reason>` only together with `@owner-gate` (e.g. owner visual acceptance). Never for logic.

**Traceability gate (F1):** `scripts/quality-gates/check_bdd_traceability.sh` parses every feature file, fails a scenario with zero or several test tags, and resolves each tag to an existing test function, SQL file or load profile. Tag-shape errors (zero or several tags, `@manual` without `@owner-gate`) are checked in every feature file, including gated ones. Resolution (does the named test exist?) is enforced only for feature files listed in `scripts/quality-gates/bdd_landed.txt`; each workstream's final task appends its feature file there. Registered in `run_all.sh` as WARN (blocking flag 0) until W2 lands; W2's final task creates `bdd_landed.txt` and makes the gate blocking for the listed features.

**Resolved is not accepted.** The gate proves a referenced test exists ("resolved"). A scenario is **accepted** only through an execution record `docs/tracker-gaps-2026-11/acceptance/<workstream>.json` (tested commit SHA, per-scenario result pass/fail/blocked/insufficient, command, fixture/deployment context, unresolved gates); `check_bdd_traceability.sh --accepted <workstream>` fails unless every scenario passed at the current HEAD. SQL scenarios count only from a DB run that executed and passed; load scenarios only from a qualification-mode run id.

**Red means missing or broken behaviour.** A red step shows a missing table/function/type or the current wrong behaviour. Never write a deliberately wrong expectation to force a failure. A temporary mutation to prove a test is not vacuous is allowed only for a test added after the code exists, labelled "non-vacuity check" and reverted in the same step.

**Definition of done for a scenario:** its tagged test exists, failed before the implementation for a real reason (recorded in the task's red step), passes after, runs in its gate (`test_packages.sh`, `test_ios_unit.sh`, `run_local_db_tests.sh`, `test_edge_functions.sh`), and is recorded as passed in the workstream's execution record.

## 5. Success parameters

### 5.1 Program-level (all must hold before a workstream is called done)
- 100 % of its feature scenarios tagged, resolved by F1, and passing.
- `run_all.sh` green (with `SKIP_IOS_BUILD=1 SKIP_IOS_TEST=1` when the owned simulator UUID is used, plus the explicit UUID test run); `check_architecture.sh`, `check_navigation.sh`, `check_branded_states.sh` at 0 offenders.
- No new warnings above the baseline; no force unwraps; every new string EN + DE.
- Backend changes: DB tests for grants (client roles cannot call service-only functions; anon can call only the explicit allowlist), RLS (cross-account reads/writes denied), and `delete-account` cleanup; EXPLAIN plan uses an index for the 2,000-title library fixture.
- Capacity: new endpoints present in the F3 workload under their class; budgets per §3 met in the next qualification run; no release of backend-traffic features while NOT QUALIFIED.
- Docs: three state docs + memory updated (Rules 1–2).

## 6. Workstream decisions (what the plans implement)

**W2 Export.** Entry point Profile → "Export your list" (a tool sheet). Formats: MAL XML (one file per medium, MAL's `myanimelist` export schema, which `MALExportParser` already reads), CSV (one file, both media, documented columns), JSON (full fidelity: Kuro ids, AniList ids, MAL ids, tags, custom lists, dates). Built on the device from `LibraryStore` plus one batched catalogue read for MAL ids and titles. Shared with the system share sheet. Free, no sign-in beyond the account the library belongs to. The privacy text names it as the data-portability route. **Corrections (2026-11-09 review):** JSON carries custom lists as separate ordered objects (`id`, `name`, `createdAt`, `items` with `medium`, `mediaId`, `position`, `inLibrary`), including empty lists and items no longer in the library, plus each entry's tracking-unit identity where present. A MAL XML file that would exceed `MALExportParser.maxBytes` (32 MiB, measured after escaping) or `maxItems` (20,000) is split into numbered, separately re-importable parts. CSV neutralises cells beginning with `=`, `+`, `-`, `@`, tab or CR by prefixing `'` (OWASP CSV-injection guidance); JSON keeps the exact text.

**W3a Alert offer.** Shown inline in the save confirmation, only when: the title has a future exact release instant, the global release toggle is off, no per-title override exists, and the account has not declined three times. It never prompts by itself; only the tap on "Notify me" reaches `toggle(_:)`. The host that draws the offer is chosen from actual visibility: the pager's selected section and the topmost navigation layer, never the order in which hosts appeared (the pager mounts the current page and its neighbours).

**W4 18+ notice.** Search: the search RPC returns a `hidden_adult` count for the query (bounded, same index), and the client shows one line under the results. Import review: unmatched rows whose match is adult are labelled "18+ — not listed in Kuro" and kept in the unresolved download.

**W5 Guest mode.** No local guest library ("explain local-only guest saving": the sign-up sheet says "Kuro keeps nothing on this phone until you have an account; the title you picked is added as soon as you sign up"). Pages available signed out: Discover, Search, Browse, title, entity and season pages. Home, Collection, Taste and Clubs show a sign-up invitation. The pending action is kept in memory for the sign-up flow and replayed once after `bootstrapAfterAuth`. Anonymous EXECUTE only for an explicit allowlist enforced by a DB test. Anonymous SELECT on catalogue tables (`anime`, `manga`) already exists for every install, because the anon key ships in the app; a client flag cannot revoke it, so the missing per-IP limit is a current production exposure (owner decision), not something guest mode introduces. W5 is last in order and blocked on D-A.

**W6 Grouping.** Display only. Group membership comes from reviewed continuity (`SeriesGrouping.decide`); anything not approved stays its own row. If any member is Watching/Reading (or Rewatching/Rereading), the group row shows that status (most recently updated such member) and +1 targets it; otherwise Planning when every member is Planning, else the most recently updated member's status. A pilot of about 10 owner-reviewed multi-season series (published through D-G, behind the flag) makes the feature visible for evaluation. A "Group seasons" switch in the Collection density controls, remembered per account (default on).

**W9 Lists and dates.** New per-user tables (UUID user ids) with RLS; writes through RPCs that respect the existing revision fence for list rows; repeat count and dates go through `LibraryEdit` (F2) to the existing `repeat_count`, `started_raw`, `finished_raw` columns. Tag and list membership changes are deltas through one atomic RPC, `apply_title_organisation_delta_v1(p_medium, p_media_id, p_add_tags, p_remove_tags, p_add_list_ids, p_remove_list_ids)`, never a whole-set replacement from a possibly stale sheet (no `set_title_organisation_v1` exists). Custom-list order uses sparse numeric positions, so a move (`move_custom_list_item_v1(p_list_id, p_item_id, p_after_position, p_before_position, p_expected_list_revision)`) writes one item row plus the list's `revision`; a move or rebalance whose expected revision is stale raises `STALE_LIST`, and the client reloads and lets the person retry once, never silently. List items survive removal of the title from the library.

**W10 Up next.** A Collection section (not Discover), so Rule 6 is untouched; one RPC that joins the caller's completed entries with relations and excludes owned titles. Plan's Undo receipt is bound to the entry the tap created (row id, lifecycle id, revision, created flag); no Undo when the title was already in the library.

## 7. Out of scope
Paid features of any kind; public reviews; global social feed; search synonyms; filler lists; MAL two-way sync (MAL registration is not approved); Android/web clients.
