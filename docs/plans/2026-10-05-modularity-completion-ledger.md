## Rulings

- **P2-R1 (policy defaults from the contract, recorded):** private individual club activity is not readable through raw table reads, while authorized aggregate counts stay correct (F34 + F36 together); owner/admin removal is separate from voluntary leave (removed users need explicit restoration before rejoining; voluntary leavers may rejoin with a still-valid invite, accurate copy); departed members' activity is excluded from current-member aggregates. No new removal screen, no reactivated server classifier. Cost if wrong: a product decision on retention; checked against the product authority before the SQL lands.
- **P2-R2 (import transaction contract, F10-F13):** the database owns one atomic transaction per Apply: accepted item writes, their journal rows and the session transition commit together or not at all. Conflicted items are reported and excluded (partial outcome), not a transaction failure; a session with at least one accepted item is `applied` and Undo-eligible, with a response `status` of `applied` or `partial` (and `success` kept false when any conflict exists, for existing callers). A client-supplied idempotency key makes a lost-acknowledgment retry return the same outcome without re-applying. Undo is one conditional transaction per session: only fields still equal to the imported after-image are reverted; a later edit or deletion is kept and reported as a skipped compensation; a failed Undo rolls back and stays retryable. Cost if wrong: response-shape additions the Swift client must read; existing fields keep their meaning.
- **P2-R3 (F02):** account-scoped presentation lifetime is implemented by keying the signed-in subtree on the account identity in `RootView` (same-user token refresh does not change the key, so legitimate state is preserved). Edit is mechanical and lead-owned in the user-dirty `KuroApp.swift`. Cost if wrong: a direct A-to-B switch resets the pager to its default page.
- **P2-R4 (F48):** the test host selects a fixture composition (fixture URL/key, in-memory auth storage, deny-all URL session) before `AppComposition.shared` builds a client. The selection is by test-host detection or an explicit launch argument and compiled for DEBUG only. Cost if wrong: a test intentionally needing real network must opt in explicitly.

- **P2-R5 (F82, alias key):** the shared alias key ignores explicit progress expressions (marker-based phrases such as "episode 5", "S2E5", "bis Kapitel 200") and keeps bare numbers, because they may be part of a title ("Mob Psycho 100", "86"). Parse still reads the legacy Apply key as a fallback so persisted aliases stay readable; no data migration. Cost if wrong: a rare alias that was keyed with progress text no longer matches the new key (the legacy fallback covers rows written by the old Apply).
- **P2-R5 amendment (accepted from L2b):** the alias key KEEPS the season number (every season notation, 'season 2', 'Staffel 2', 'S2E5', '2x05', becomes one token `s2`) and drops only the episode/chapter part. Reason: the catalog has one entry per season and an alias adds +0.80 to the entry it points at while a season match adds only +0.18 (auto-apply fires at 0.85), so stripping the season could auto-apply progress onto the wrong season's row. Cost if wrong: an alias learned for one season does not carry over to another.
- **P2-R6 (F72/F73/F76 from L2b):** F72 the generic finished/completed/done branch follows the same partial/position rule as "I finished" (a write-safety fix); F73 the fallback secondary rail is built only when no candidate exists; F76 a non-finite recommend `limit` defaults to 8. F74 and F75 stay OPEN as product decisions (subject-less status verbs; bare-number unit question). Cost if wrong: F72 changes the stored status for "finished X up to episode N" from COMPLETED to WATCHING.
